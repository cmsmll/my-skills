# clearing-doubts — 消除疑惑

执行用户任务或需求时，遇到**真正需要用户决策**的不明确之处，停下来用 `ask` 一次性列出多个问题让用户选择，得到答案后再继续。不要憋着疑问硬做，也不要拿无关紧要的细节反复打断。

## 核心原则

- **只在「无法自行决定」时问**。能从代码、文档、会话上下文推断出来的，自行决定并在交付说明里声明假设；问了反而拖慢节奏。
- **一次 ask 问多个问题**（通常 2-5 个），不要一个问题一问。每个问题给 2-5 个简洁选项，并标注推荐项（`recommended`），降低用户决策成本。
- **问题要带背景与影响**：说明现状、为什么有歧义、选各选项的后果，让用户基于事实选择，而不是猜。
- **先做足功课再问**：动手前先读相关代码/文档、必要时查资料确认技术前提，确保选项描述真实可行（例如某字段能否取到、某接口是否可用），不把没验证过的选项摆给用户。
- **可自行推断的细节不放进问题**：记为假设，按假设执行；用户答案与假设冲突时以用户答案为准，并说明调整。

## 执行步骤

### ① 判定是否需要停下来问

**必须问**（影响实现方向，问错了返工成本高）：
- 任务措辞有歧义，且不同理解产生不同结果（如数据口径、计算方式、结构设计、命名）；
- 任务描述与代码/文档现状冲突，无法判断以谁为准；
- 破坏性操作（删除/覆盖文件、迁移数据、改公共接口）需要用户授权；
- 选择会成为后续所有工作的契约（输出格式、schema、接口、目录结构）。

**不用问**（自行决定 + 声明假设）：
- 代码/文档/上下文里已有答案；
- 各选项结果差别不大、怎么选都合理的细枝末节；
- 用户已明确表达过的事项。

### ② 提问前准备

1. 读相关代码/文档，梳理「现状 vs 任务」的差异清单——问的问题必须基于这份清单，而不是凭感觉。
2. 对影响选项可行性的技术前提先调研（读文档、查资料），确认选项描述真实。
3. 把能自行推断的细节列为假设，不进问题。
4. 把真正需要用户决定的点整理成问题，控制在 2-5 个，按重要性排序。

### ③ 调用 ask

一次调用包含多个 question，每项结构：

- `i`（intent）：简短，如「确认输出结构改造细节」；
- `id`：简短英文标识，如 `mcap`；
- `header`：中文短标签，如「总市值」「文件命名」；
- `question`：背景 + 现状 + 影响。模板：「「XXX」具体口径？现实现是 YYY，导致 ZZZ 的问题。」「输出里的 X 是 Y 的笔误，还是就用 X？」「X 用哪种结构？区别是 …」；
- `options`：2-5 个，`label` 短而可扫读（如「历史总股本 × 不复权收盘价」），`description` 放差异与影响；
- `multi`：多数 `false`；确实需要多选时 `true`；
- `recommended`：给出推荐项索引，并说明理由（更贴近用户原意/修正明显问题/风险更低）。

常见问题类型模板：
| 类型 | question 模板 | 选项示例 |
|---|---|---|
| 口径 | 「「XXX」具体口径？现实现用 Y，导致 Z。」 | 2 个候选口径 + 各自影响 |
| 命名/笔误 | 「X 是 Y 的笔误，还是就用 X？」 | 修正为 Y / 按字面 X |
| 结构/格式 | 「X 的内容结构用哪种？」 | 候选结构 + 适用场景 |
| 破坏性操作 | 「旧的 X 怎么处理？（列出内容，注明可重新生成）」 | 删除 / 保留 |

### ④ 收到答案后

1. 按用户选择执行；用户用自定义输入回答时，以自定义输入为准（优先级：自定义输入 > 选中项 > 推荐项 > 假设）。
2. 答案与事先假设冲突 → 以答案为准，向用户说明调整点。
3. 继续原任务，已确认过的事项不再重复问。

## 注意事项

- 一次只问真正必要的；问题过多拖慢节奏，能推断的不问。
- 选项 `label` 要短；`description` 放差异与影响，不放废话。
- 问题里只放会改变实现方向的选择；问完得到答案前不开始动手改代码。
- 破坏性操作必须单独成问并说明影响范围与可恢复性，不能混在普通问题里一带而过。
